# 定位优化测试版

历史版本：2.2.0-test.2。分支：`codex/test-seek-performance`。基线：正式版 2.1.0。本记录保留当时的策略与测量条件，不代表后续测试版的默认配置。本次只交付测试包，不合并main、不发布正式Release。

## 交互与解码

- 进度条和屏幕横滑共用拖动会话。保持人物控制点、非线性手感和连续的目标位置显示。
- 拖动期间静音，由当前播放器产生画面与小预览，不另开预览解码器。首个中间请求延后至按下50ms；快速点击在松手时只提交最终定位。持续移动保留最新待处理目标，基础间隔80ms；Media3尚未产生新帧时，替换间隔最多延至180ms。
- Media3在实际提交中间请求时启用scrubbing，采用前后各250ms容差，并保留音频轨道，避免反复拆建。松手提交最终EXACT；取消回原位置，保留播放/暂停意图，系统中断后不擅自恢复。
- LibVLC拖动使用fast seek，松手取消待处理的中间请求并提交一次precise seek。原本播放时保持原生时钟运行并静音，原本暂停时保持暂停，避免额外的暂停/恢复周期。文件缓存显式设为250ms，避免硬解配置补入1500ms；缓存数值不是每次定位的固定等待时间。
- 原生音频使用AudioTrack，拖动、预载及非当前页面维持音量门控。排除了OpenSLES零音量边界问题；应用静音验证使用非零系统媒体音量，不能以手机总音量为零证明应用静音。
- API34及以上原生输出使用SurfaceView，旧系统保留TextureView。预览复用当前播放器的表面，PixelCopy最多一项进行中，图片只留在有界内存。首帧确认和预览请求使用表面代际，防止重建后沿用旧画面。
- 显示表面实际销毁时重新绑定输出，保留同一播放器；暂停恢复重新确认原位置的画面。原生软硬解回退按播放器实例交接音频焦点，静音状态不会被压低音量/恢复音量回调绕过。
- 进度栏时间表示手指目标；VLC预览时间使用近似播放时钟，不宣称是画面的精确PTS。没有获取到新画面时不伪造预览，首帧可用也不等于目标帧已精确呈现。
- 相邻视频分阶段准备，在当前画面就绪后先准备下一页，再准备上一页。仍需首帧就绪才能滑入，翻页不重建已准备的播放器。
- 备用缩略图提取器限制在 4 MiB 内存；交互路径不启动 VLC 软件取帧，慢取帧自动降频，停止使用后释放资源，不保存图片文件。

## 自动选择的边界

自动模式优先LibVLC，Media3作为兼容回退；测试工具可以单独指定引擎，界面不增加手动选项。不在每次打开时同时运行两个引擎比较速度。当前页与相邻预载页采用相同选择规则。

原生软硬解选择独立于引擎选择。当时自动软解仅对已验证的一款Android14/API34实机开放，并同时要求文件头明确为8-bit AVC、帧率已知且不超过30fps、长边不超过1920和短边不超过1080、没有HDR标记。未知信息、高规格视频及其他设备采用硬解优先；不能仅按MP4等扩展名判断。

只为请求播放/预载的文件后台读取媒体头；单工作线程、最多8项等待任务、128项内存缓存。150ms内没有结果则本次选择硬解，迟到结果仅缓存供以后打开，不中途重建播放器。普通媒体库刷新不探测全库码流。

软解错误先尝试原生硬解，必要时再转Media3。正常前台1倍速播放时，两个连续2秒统计窗口出现明显丢帧或呈现不足，可尝试硬解；定位、暂停、缓冲、后台和缺失统计不作为持续解码能力证据。该监测不能识别所有冻结，也不测量精确定位耗时。

只有替代引擎实际产生首帧后才记住对应回退：软解失败与整个LibVLC失败分开记录，冷却24小时，避免循环重建。记录仅在本机、最多64项，以文件身份、大小、修改时间、系统和引擎版本区分；退出页面时写入，不逐帧写盘。

本版没有逐文件测出并保存“最快引擎”。实测适用范围、落点误差和速度必须一起报告；编码、关键帧间隔、设备负载仍会影响体验，不承诺所有视频零等待。

## 分析与验证

REA检查用户提供的VLC3.7.2安装包，确认其“拖动fast、松手precise”调用链；JNI与原生调度另由共享Ghidra及固定上游源码交叉核对。真机确认参照VLC在指定H.264样片中走avcodec软件路径，不能只比较播放器名称或假设双方都在硬解。原生队列、preroll、音量边界和来源说明见 [VLC原生定位调度](VLC_NATIVE_SCHEDULING.md)。

本机分析材料位于 `dist/analysis/vlc-20261101`，原始 APKS 与反编译证据不进入源码仓库。

状态回归检查覆盖真实预览、最新目标、取消、暂停与系统中断、片尾、释放、三窗口复用、单路声音及循环。Media3保留其精确帧检查；原生暂停状态检查明确允许目标前后200ms（25fps样片的5帧），以覆盖已观察到的原生preroll提前落点。这个边界用于状态恢复回归，不证明逐帧精确，也不能将此前100ms检查的失败改称通过。

独立光学性能测量继续采用120ms容差，未随状态测试放宽。通过屏幕中编码的帧号读取实际画面，分别记录首次变化、接近目标、稳定落点以及有符号误差；负值表示提前。暂停点击至少观察1秒，并要求新画面稳定300ms。超出容差的稳定画面标为`settled-outside-tolerance`，不冒充持续加载或删除样本；完整收集后再判断准确性。截图有采样开销，结果是观测区间，不证明零延迟。

测试输入需校准进度条实际范围，核对应用、文件、轨道、播放状态及系统音量；比较采用相同目标和测量协议。原始报告保留每次落点与误差，参照VLC本身的提前落点也照实记录。操作方式和重放参数见 [测试工具说明](../scripts/qa/README.md)。具体运行结果随测试包的`VERIFICATION.txt`提供；模拟器与生成样片不能代替用户手机上的问题视频。

映序暂停18个落点均在120ms内，其中H.264可能提前80–120ms，HEVC可能提前80ms。VLC HEVC有2/6个稳定落点提前160ms，表中仍计入其画面出现时间，不能把这个速度当成精度通过。映序播放中HEVC另有1/6次在596–687ms区间才出现目标画面，其余5次在127–170ms内观测到；没有用中位数隐藏这条慢样本，仍不承诺每次定位零等待。

每隔120ms连续点击六个位置，最后一次按下至目标画面的有效观测区间如下。每格是一条完整队列，样本量不足以作普遍排名。

| 样片 | 映序 | VLC |
| --- | ---: | ---: |
| H.264 720p | 23–123 | 82–157 |
| H.264 1080p / GOP10s | 230–315 | 176–279 |
| HEVC 1080p | 72–165 | 330–389 |

这组结果支持响应达到相近范围、部分场景更快，不证明逐次都优于VLC。先前有效队列的HEVC结果也有映序66–173ms、VLC79–168ms，说明单次测量有波动。无效记录全部保留：一次并发测试中断、一次VLC目标窗口缺少有效条码、一次VLC后续请求未体现在画面中、一次VLC控制栏未定位成功；它们未算作解码超时。最后一类和请求未体现的原因尚未确定。

额外强制HEVC软解时，播放中6次观测上界134–212ms，但暂停的4/6次没有取得新的稳定目标画面，另一次提前160ms。该路径没有被纳入自动软解规则；实际配置通过运行字段核对，覆盖值在测试结束后恢复。

## 构建与安装

Java17、Android SDK36（compileSdk36、targetSdk35、minSdk26），Media3 1.8.0与LibVLC 3.7.7。使用项目现有构建工具和签名配置：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build.ps1 assembleRelease -PpreviewInstall=true --offline
```

该命令构建包名为`io.mediamaster.app.preview`的测试包，沿用本机现有测试签名；与已安装版本的包名及签名一致时可覆盖安装并保留数据。不要通过卸载绕过签名不匹配。正式更新仍须保留对应签名并递增版本号。
